What it does
AuthenticatedSessionStep.execute(context) calls authenticator.is_authenticated_session(context.auth_session). This checks two things simultaneously: first, that the session ID exists in the active session store; second, that it has not exceeded the configured timeout (default 300 seconds). If the session is still valid, touch_session() is called to refresh the last-activity timestamp, preventing premature expiry during an active interaction.
If it passes
Control moves immediately to Step 2 (RBAC). No event is written for a passing session check — it is silent by design, since every request must pass this gate and logging it would fill the audit log with noise.
If it fails
AuthenticationError is raised. The request is stopped here. core_banking.py is never touched. No banking operation is attempted. The caller receives an error indicating the session is not authenticated.
Why this step is first
There is no point evaluating permissions, rate limits, or fraud rules for a request that has no valid identity. Placing this step first eliminates the computational cost of all subsequent checks for unauthenticated requests, and prevents any downstream component from receiving an untrusted AuthSession.
Design pattern
This is step one of the Chain of Responsibility pattern. AuthenticatedSessionStep implements ISecurityStep. The method supports(OperationType.READ) and supports(OperationType.MONETARY) both return True — this step applies to all operation types, read and monetary alike.
What it does
AuthorizationStep.execute(context) calls authorization_policy.check_permission(user, action, account_number). The policy looks up the role assigned to this user on this specific account number, then checks whether that role holds the required permission. ROLE_OWNER holds PERM_DEPOSIT, PERM_WITHDRAW, and PERM_TRANSFER. ROLE_AUDITOR holds none of these — it is read-only.
If it passes
Control moves to Step 3 (Rate Limit). No audit event is written for a passing authorisation check.
If it fails
Before re-raising AuthorizationError, the step writes an ACCESS_DENIED security event with EventStatus.DENIED and Severity.WARNING to the account's audit logger. This event is immutable and permanently preserved. The request stops here.
Why this step is second
Authorisation is meaningless without a verified identity. Conversely, it must precede rate limiting because a user who has no permission at all should never consume rate-limit quota — rejecting them at this gate is cheaper and more informative than letting them reach Step 3.
Design pattern
AuthorizationStep implements ISecurityStep. supports(OperationType.READ) and supports(OperationType.MONETARY) both return True — RBAC applies to both read and write operations.
What it does
RateLimitStep.execute(context) calls rate_limiter.is_allowed(username, action). The rate limiter is user-scoped (not session-scoped), meaning the limit applies to the user across all their sessions simultaneously. Two interchangeable strategies are available: TokenBucketRateLimiter permits requests as long as tokens remain and refills gradually; StrictWindowRateLimiter enforces a hard ceiling within a fixed time window and resets at the window boundary.
If it passes
Control moves to Step 4 (Fraud). One token is consumed from the bucket, or one request is counted within the current window. No audit event is written for a passing rate check.
If it fails
The step writes a RATE_LIMIT_EXCEEDED security event with EventStatus.BLOCKED and Severity.WARNING to the audit logger. Then RateLimitExceededError is raised. The request stops here. The account balance is untouched.
Why this step is third — not last
Rate limiting must precede fraud detection because the fraud engine performs actual computation (building a TransactionContext, querying TransactionMonitor, evaluating four rules). An attacker flooding the system with requests must be stopped before they consume the cost of fraud evaluation. Rate limiting is cheap; fraud detection is relatively expensive.
Design pattern
RateLimitStep implements ISecurityStep. supports(OperationType.MONETARY) returns True; supports(OperationType.READ) returns False — rate limiting is applied only to monetary operations, not to balance enquiries.
What it does
FraudCheckStep.execute(context) constructs an immutable TransactionContext — a frozen dataclass containing the username, account number, action, current balance, requested amount, recent action count (from TransactionMonitor), and the current hour of day (from the injected IClock). This context is passed to FraudDetectionEngine.check(tx_context), which evaluates every injected fraud rule against it via polymorphic dispatch.
The four fraud rules
LargeAmountRule — amount exceeds the configured threshold.
RapidOutgoingTransactionRule — recent_action_count exceeds the velocity limit.
BalanceRatioRule — amount / current_balance exceeds max_ratio.
UnusualHourRule — hour_of_day falls outside the permitted window.
If all rules pass (no rule triggers)
Control moves to Step 5 (Execute). No fraud event is written.
If any rule triggers
A FRAUD_DETECTED security event with EventStatus.FLAGGED and Severity.CRITICAL is written to the audit logger. CriticalEventPublisher immediately notifies all registered AlertObserver instances. FraudAlertError is raised. The account balance is not modified — no funds leave the account.
Why this step is fourth — just before execution
Fraud evaluation requires knowing the current account balance and recent transaction history — information that only makes sense at the point of execution. It cannot be performed earlier in the pipeline without those values. It must, however, run before the actual deposit() or withdraw() call so that suspicious transactions are blocked before any money moves.
Design pattern
FraudCheckStep implements ISecurityStep. The engine uses polymorphism (Strategy pattern) — it calls rule.evaluate(context) on every IFraudRule without knowing which concrete rule is being evaluated. Each rule is independently replaceable (LSP) and new rules may be added without modifying the engine (OCP).
What happens at execution
All four security gates have passed. SecureAccountOperationService calls the banking operation directly on the Account object — either account.deposit(amount) or account.withdraw(amount). This is the only point in the entire system where core_banking.py is invoked.
What happens immediately after
1. The account's audit logger records a DEPOSIT or WITHDRAW event with EventStatus.PASS and Severity.INFO.
2. TransactionMonitor.record() logs this operation for future use by RapidOutgoingTransactionRule.
3. The updated balance is returned to the caller.
The critical design point
core_banking.py has no knowledge of the four gates that preceded this call. BankAccount.deposit() simply validates the amount and adds it to the balance. The security guarantee is entirely structural — it comes from the pipeline architecture, not from any logic inside the banking domain itself. This is the practical realisation of keeping the core domain independent from the cybersecurity layer.
What about a read operation (get_balance)?
A balance enquiry only passes through Steps 1 and 2 (Session and RBAC). Steps 3 and 4 — rate limiting and fraud detection — return False from supports(OperationType.READ) and are skipped entirely. SecurityStepResolver filters the applicable steps at runtime based on the operation type.

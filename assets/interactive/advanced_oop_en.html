Advanced OOP principles applied to the secure banking project

1 SOLID principles — how they are applied in the project −
S — Single responsibility
Every class in the project is assigned one, and only one, concern. CredentialService validates credentials only. SessionManager manages session lifecycle only. ThreatReportBuilder constructs threat reports only. BoundedSecurityEventStore stores security events only. Should the reporting logic change, only ThreatReportBuilder is modified — no other class is affected.
Why? — Reduces coupling between components and makes every unit independently testable.
O — Open/closed
A new fraud rule is introduced by creating a class that implements IFraudRule and injecting it into FraudDetectionEngine — not a single line of the engine is modified. The same principle governs adding a new rate-limiting strategy via RateLimiterFactory.
Why? — The system extends without risk of breaking existing behaviour.
L — Liskov substitution
TokenBucketRateLimiter and StrictWindowRateLimiter both implement IRateLimiter and are fully interchangeable — the calling code is entirely unaware of which is in use. The same holds for all four fraud rule implementations.
Why? — Complete flexibility to swap strategies at runtime without modifying any consumer.
I — Interface segregation
Interfaces are small and purpose-specific. IClock exposes only now(). IFraudRule exposes only evaluate() and description(). IAccountAuditLogger exposes only what the audit layer requires. No class is forced to implement methods it does not use.
Why? — Simplifies writing test doubles (e.g. TestClock) and reduces unnecessary coupling.
D — Dependency inversion
FraudDetectionEngine holds no knowledge of any concrete rule — it depends solely on the injected IFraudRule list. SecureBankingServiceFactory serves as the composition root, assembling all dependencies in one place. Inner classes never construct their own collaborators.
Why? — Full testability: in the test suite, TestClock is injected in place of SystemClock without modifying any production code.
2 Abstraction & interface-based design +
The Account class in core_banking.py is an abstract base class that defines a contract of four operations (deposit, withdraw, get_balance, account_number) without any implementation. Everything that interacts with accounts depends on this abstraction — not on BankAccount directly.

Throughout the security layer, every boundary is defined as an ABC: IClock, IFraudRule, IRateLimiter, IPasswordPolicy, IPasswordHasher, ISecurityEventFactory, IAccountAuditLogger, IAlertObserver.

Collaborating classes address only these interfaces — never the concrete implementations behind them.
Consequence: any implementation (e.g. replacing PBKDF2PasswordHasher with a different hashing algorithm) may be substituted without modifying any consuming class.
3 Encapsulation — preserving internal state integrity +
All internal fields across every class are defined as self._field (private by convention in Python). No external class may access or mutate them directly.

Specific examples from the codebase:
  • BankAccount._balance — the balance is modified only through deposit() and withdraw(). _validate_amount() and _round_money() are applied internally before every operation.
  • BoundedSecurityEventStore._events — the event list is hidden. No class may append events except through the designated append() method.
  • LoginAttemptPolicy._attempts — the failed-attempt counter is hidden and cannot be reset from outside the policy itself.
  • SecurityEvent — declared as @dataclass(frozen=True), which prevents any mutation after creation, even from within the same module.
Consequence: no part of the system can corrupt the state of another — each class is solely responsible for the integrity of its own internal state.
4 Polymorphism +
Polymorphism is employed at three principal points in the design, each of which instantiates the Strategy pattern:

A — Fraud rules
FraudDetectionEngine.check(context) calls rule.evaluate(context) on every rule in the injected list. Whether the rule is a LargeAmountRule, a BalanceRatioRule, or an UnusualHourRule, the engine treats them identically through the shared interface.

B — Rate-limiting strategies
RateLimitStep calls limiter.check_rate_limit(username) on whichever limiter has been injected — Token Bucket or Strict Window — through the same IRateLimiter interface.

C — Account operations
DepositOperation and WithdrawOperation in core_banking.py both implement Operation.apply(account, rng). TransactionSimulator treats them identically.
Consequence: introducing new behaviour requires only a new class implementing the relevant interface — no modification to any consuming code.
5 Composition over inheritance +
The project avoids deep inheritance hierarchies entirely. In their place:
  • FraudDetectionEngine receives an injected list of rules — it does not inherit rule logic from any class.
  • SecurityOperationPipeline receives an injected list of ISecurityStep instances — it does not inherit step logic.
  • AuditedAccountService wraps AccountOperationAdapter — this is the Decorator pattern achieved through composition, not inheritance.
  • SecureBankingService (the Façade) receives all its services injected by SecureBankingServiceFactory.
Consequence: no fragile inheritance chains are created. Every component may be substituted or tested independently.
6 Immutable value objects +
Four value objects are declared as @dataclass(frozen=True, slots=True):
  • SecurityEvent — the audit record cannot be altered after creation. This guarantees the integrity of the audit trail.
  • TransactionContext — the context passed to fraud rules. No rule may modify it.
  • TokenBucketConfig / StrictWindowConfig — rate-limiter configuration is fixed after construction.
  • SecurityConfig — the full platform configuration is protected against accidental mutation.
frozen=True means Python itself enforces immutability — this is not merely a naming convention.
Consequence: automatic thread safety and a structural guarantee that no component may falsify the audit record.
7 Core domain independence +
core_banking.py imports nothing from security_layer.py, secure_banking_services.py, or security_reporting.py.

BankAccount is entirely unaware of the security layer. It executes deposit() and withdraw() as pure domain operations. The security layer wraps around it externally — via AccountOperationAdapter and AuditedAccountService — without touching the original code.

This separation is structural, not merely conventional: core_banking.py can be executed in full independence in an environment that contains no security files whatsoever.
Consequence: banking logic is tested in complete isolation; the security layer is tested in complete isolation. Neither depends on the other.
